# Spec：{任务标题}

> 用途：任务开始前定义「做什么 + 验收」，完成后按此关闭。
> 使用：复制本文件为 `spec-<slug>.md`，填 `[ ]` 内容，删掉本注释块。

## 目标

一句话说明这次变更要达成什么用户可见/可观察结果。

## 背景（可选）

触发原因、关联分册（架构/规则/pitfalls）、依赖的前置变更。

## 范围

### 做（In）
- [ ] 要改的文件/模块清单
- [ ] 具体行为变更点

### 不做（Out）——防范围蔓延
- [ ] 明确排除的改动（如：不重构无关代码、不动依赖、不改配置）

## 设计要点

- 分层归属（前端洋葱/后端 DDD）：本变更落在哪一层，依赖方向是否合规。
- 数据流：输入 → 处理 → 输出（涉及存档字段时标注序列化/回档两处都要改）。
- 性能/GC：若进每帧循环，说明复用策略。
- 边界条件：空值、越界、并发、异常降级。

## 验收标准（DoD）

每项必须**可机器或可观察验证**：

- [ ] 行为：具体断言（如「点击 X 后 Y 变为 Z」）
- [ ] 构建：`node scripts/verify.mjs commit` 全绿（tsc advisory 项单独列出）
- [ ] 分层：`check-layering` 无违规（若涉及前端 import）
- [ ] 兼容：旧存档/旧场景版本回档不丢字段（若涉及数据）
- [ ] 回归：{受影响的最小回归场景清单}

## 边界 / 风险

- 已知妥协与理由
- 回滚方案（改哪个文件可恢复原状）

## 关闭记录

- [ ] 验收全过日期 / 结果
- [ ] 本 spec 归档或删除（防过期堆积）
